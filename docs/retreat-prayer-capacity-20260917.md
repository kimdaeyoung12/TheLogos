# 공동기도 50명 성능 검증 — 2026-09-17

## 판정

**사용자 승인으로 DB 연결 풀을 2→5로 확대한 뒤 50개 고유 인증 + 100개 실시간 채널 시험 통과. 풀 5 유지. 프런트엔드 변경은 아직 배포하지 않음.**
현재 작업 트리의 개선안에 대한 결과이며 운영 서비스 전체의 무지연 보증이 아니다.

## 승인 후 연결 풀 5 재시험

동일한 50개 고유 세션과 16초 가입 분산으로 재시험했다. 최초 시도는 인증 토큰 갱신의 429 오류로 39/50에서 중단되어 풀을 2로 복원했다. 인증 초기화를 1초 간격으로 분산한 재시험은 성공했고, 성공 후 풀 5를 유지했다. 익명 가입 제한은 30이며 요금제는 변경하지 않았다.

| 항목 | 풀 5 결과 |
|---|---|
| 첫 화면 API 50개 | p95 1,950ms / 최대 1,962ms |
| 실시간 구독 50개 | 분산 포함 최대 16,959ms, 재시도 0 |
| Presence 가입 및 전원 수치 일치 | 해당 단계 총 18,880ms, 재시도 0 (풀 2: 48,994ms) |
| 홈→같이 기도 이동 | 수치 일치까지 18,080ms |
| 100채널 유지 중 상태 동시 조회 | p95 394ms / 최대 399ms |
| 음원 64KB 동시 요청 | 50/50 HTTP 206, 최대 807ms |
| 10개 연결 복구 | 8,087ms |
| 30초 유지 | 50/50 동기화, 최종 오류 0 |

Presence 시간은 가입 단계 자체의 측정이며 페이지 진입부터의 총 소요 시간이 아니다. 실제 관리자 송출 RPC를 운영 중 변경하는 시험은 하지 않았다. 아래 풀 2 결과는 비교용 이력이다.

## 변경안

- 가입 분산 단축(3초/6초)은 실제 시험에서 시간 초과가 있어 채택하지 않음. 실시간/인원 표시 모두 기존 16초 분산 유지.
- 실시간 연결 이후 고정 16초 추가 대기만 제거.
- 실시간 연결 준비/복구 중에는 화면이 보일 때만 2초 주기로 기도 상태를 확인. 한 번에 한 요청만 허용하며 정상 연결 시 중지.
- 최초 인원 표시 연결 실패 후 자동 재시도. 화면 이동/종료/재초기화 시 오래된 재시도 무효화.
- 최초 실시간 가입 직후 상태를 다시 확인하여 첫 HTTP 조회와 가입 사이 변경을 보완.
- HTTP 조회 성공을 소켓 복구로 오인하지 않도록 연결 상태 구분.
- 완전한 실시간 행은 즉시 표시하고 불완전한 행만 전체 재조회. 프로그램 스냅샷을 임의 병합하지 않음.
- 새 완전한 이벤트보다 오래된 진행 중 조회 결과는 무시.
- 동일한 기도문은 매초 DOM을 다시 생성하지 않음.
- 첫 로딩의 설정/콘텐츠 버전 조회를 병렬화. 콘텐츠 버전 전후 비교는 유지.

## 실제 운영 서버 읽기 전용 측정

한 PC에서 한 차례씩 실행. 단계/공지/기도제목/권한/음악 설정을 변경하지 않았다.

| 대상 | 결과 |
|---|---|
| 전체 첫 화면 API 흐름 50개 동시 실행 | 50/50 성공. 중앙값 1,600ms, p95 1,834ms, 최대 1,846ms |
| 실제 등록 음원 첫 64KB 50개 동시 요청 | 50/50 HTTP 206 및 각 65,536바이트 확인. 총 3,276,800바이트. 중앙값 1,263ms, p95 2,667ms, 최대 2,744ms |
| 50개 고유 익명 계정 발급 | 30개 성공 후 31번째에서 HTTP 429 `over_request_rate_limit`. 실제 실시간 통합 단계에 진입하지 못함 |

음원 범위 요청은 파일 전체 다운로드, 장시간 끊김 없는 재생 또는 휴대폰 통신 품질을 검증한 것이 아니다.
테스트 익명 인증은 로컬 로그아웃했으나 서버의 익명 사용자 레코드는 삭제하지 않았다.
위 30개 제한 실패 이후 사용자 승인으로 익명 가입 제한을 일시적으로 30→100으로 올려 50개 고유 계정을 발급했다.
각 변경 실행은 finally에서 원래 값 30으로 복원하고 GET 재조회로 확인했다. 현재 테스트 세션은 DPAPI 암호화된 Git 제외 파일에만 보관해 재사용한다.
서버 익명 사용자 레코드는 삭제하지 않았다. 관리자 권한/기도 콘텐츠/요금제는 변경하지 않았다.

## 실제 50세션 통합 시험 (자동 복구 포함)

테스트 세션 재사용, 기도 상태와 콘텐츠 실제 읽기, 실제 PostgreSQL Changes 구독, 실제 Presence.
Presence는 운영 표시를 부풀리지 않도록 이미 허용된 별도 방 `retreat-prayer:presence:live`를 사용했다.
가입/이동은 16초에 균등 분산했고, 참가자 구독은 실제 RealtimeSetupCoordinator를 사용했다.
인원 표시 실패는 5초 + 분산 지연 후 최대 3회 시도했다. 실제 앱의 무한 재시도와 시험의 유한 횟수 제한은 다르다.

| 대상 | 결과 |
|---|---|
| 고유 인증 | 서로 다른 사용자 50개 확인 |
| 첫 화면 API 50개 | p50 4,698ms / p95 4,796ms / 최대 4,807ms |
| 실시간 기도 상태 가입 50개 | 분산 대기 포함 p95 17,485ms / 최대 18,157ms |
| 인원 표시 가입 50개 | 재시도 3회 발생. p95 42,728ms / 최대 47,744ms, 전원 수치 일치까지 총 48,994ms |
| 홈→같이 기도 이동 | 분산 대기 포함 최대 15,770ms, 전원 수치 일치까지 총 18,000ms |
| 100개 채널 연결 상태에서 기도 상태 동시 조회 | p50 699ms / p95 727ms / 최대 896ms |
| 50개 음원 범위 요청 | HTTP 206 모두 성공, p95 1,407ms / 최대 1,575ms |
| 10개 연결 단절/복구 | 새 연결/인원 상태 확인까지 13,465ms |
| 이후 30초 유지 | 50개 모두 인원 동기화 유지, 최종 실패 0 |

이 시험 전 6초 가입 분산에서는 기도 상태 구독 재시도 35회, p95 66,188ms였다.
16초 분산 + 인원 표시 재시도 없는 시험에서는 48개 성공, 마지막 2개 TIMED_OUT이었다.
실패 결과를 포함해 판단하므로 **기능 복구 통과 ≠ 초기 지연 해소**다.
위 통합 시험 이후 최초 가입 직후 재조회와 소켓/데이터 상태 분리도 추가했으며 단위 테스트로 검증했다.
최종 설정 변경 뒤 재시험 결과는 위의 풀 5 항목을 참조한다.

## 서버 측 병목 단서 (읽기 전용 확인)

Management API에서 현재 설정을 확인했다: 동시 접속 200, 초당 이벤트 100, 초당 Presence 이벤트 20,
초당 가입 100, 연결당 채널 100, 실시간 DB connection_pool 2, private_only true.
최근 45분 Realtime 로그를 원문/개인정보 대신 분류 집계했다: DB connection unavailable 35건,
timeout 17건, 기타 pool 관련 59건. 다른 운영 연결도 포함할 수 있는 시간창이므로 각 오류와 특정 테스트 세션의 직접 대응은 미확인.
이 설정과 로그는 풀 변경 전 관측이다. 이후 사용자 승인으로 connection_pool 2→5 시험을 수행했고 위와 같이 개선을 확인했다. 요금제 변경은 요청/실행하지 않음.

준비 화면 오표시/JS 오류/가로 넘침 0. 이 값은 로컬 격리 환경 측정이며 실제 모바일 네트워크 지연은 아니다.

## 자동 검증

`npm run test:retreat-prayer`: 82개 통과. 제어권 복원, 불완전 이벤트, 최신 버전 보존,
완전한 이벤트의 무조회 처리, 중복 요청, 해제된 구독의 늦은 응답 등을 포함.

## 남은 검증과 승인 경계

- 서버 연결 풀 변경 승인 및 동일 50개 인증 재측정 완료. 풀 5 유지.
- 운영 인원 수에 섞이지 않도록 기존 허용된 별도 `retreat-prayer:presence:live` 채널을 사용하도록 구성됨.
- 가입 제한은 승인받아 일시 상향 후 30으로 복원 확인 완료. 가입 분산 간격 단축안은 폐기.
- 초기 인원 표시 지연이 남아 있으므로 50명 무지연을 확정하지 않음.
- 실제 관리자 송출의 end-to-end 검증은 분리된 스테이징 또는 운영 기도회와 겹치지 않는 승인된 시험 시간이 필요함.
